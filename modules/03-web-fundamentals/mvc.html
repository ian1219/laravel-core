In one sentence

MVC splits an app into three jobs: Models handle data, Views handle what people see, and Controllers connect the two.

🍽️Picture a restaurant. The waiter (Controller) takes your order, the kitchen (Model) prepares the food from what's in the pantry (the database), and the plated dish (View) is what you actually see. The waiter never cooks, and the chef never visits your table.

Why it matters

A place for everything

🗂️

You'll always know where to look

A bug in the page layout? Check the View. Wrong data? Check the Model. Every Laravel project follows the same layout.

♻️

Reuse instead of repeat

One Post model serves the blog page, the admin panel and the API. Write the data logic once.

Step by step

Follow /posts through MVC

Don't worry about memorising the syntax yet. Each piece gets its own lesson later; this is the tour.

  1. The route points at a controller

    The route is the doorway. It doesn't do any work itself; it just says “for GET /posts, ask PostController's index method”.

    
          use App\Http\Controllers\PostController;

          Route::get('/posts', [PostController::class, 'index']);

  2. The Model knows about data

    A Model is a PHP class that represents one table. Post maps to the posts table and gives you methods to query it, so you rarely write SQL by hand.

    
          <?php

          namespace App\Models;

          use Illuminate\Database\Eloquent\Model;

          class Post extends Model
          {
              protected $fillable = ['title', 'body'];
          }

  3. The Controller coordinates

    The Controller asks the model for data and picks a view to show it. Notice how short it is. A good controller is a manager, not a worker.

    
          <?php

          namespace App\Http\Controllers;

          use App\Models\Post;

          class PostController extends Controller
          {
              public function index()
              {
                  $posts = Post::latest()->get();       // ask the Model

                  return view('posts.index', ['posts' => $posts]);   // hand to the View
              }
          }

  4. The View only displays

    The View is a Blade template: mostly HTML with a few placeholders. It receives $posts and loops over them. No database calls here.

    
          <h1>Latest posts</h1>

          @foreach ($posts as $post)
              <article>
                  <h2>{{ $post->title }}</h2>
                  <p>{{ $post->body }}</p>
              </article>
          @endforeach

  5. Put it all together

    Here's the full round trip. Each box has one job and hands off to the next.

Common mistakes

Avoid this, do that

❌ Avoid

          @foreach (\App\Models\Post::all() as $post)
              <h2>{{ $post->title }}</h2>
          @endforeach

Querying the database inside a view mixes jobs and hides slow queries where nobody looks.

✅ Do

          // Controller
          return view('posts.index', [
              'posts' => Post::all(),
          ]);

Fetch data in the controller (via the model) and pass it into the view.

❌ Avoid

          public function store(Request $request)
          {
              // 80 lines of pricing maths,
              // emails, PDF generation...
          }

A “fat controller” is hard to read, hard to test and impossible to reuse.

✅ Do

          public function store(Request $request)
          {
              $post = Post::create($request->validate([...]));
              return redirect()->route('posts.show', $post);
          }

Keep controllers thin: receive, delegate, respond. Bigger logic moves to models or service classes.

💡 Pro tip: the “one job” test

Before writing a line of code, ask “is this about data, display or coordination?” The answer tells you which file it belongs in.

Recap

Key takeaways

  • Model = data and rules (app/Models).
  • View = presentation, HTML via Blade (resources/views).
  • Controller = the coordinator between request, model and view (app/Http/Controllers).
  • Routes aren't part of the acronym, but they decide which controller runs.
  • Views never query the database; controllers stay thin.
