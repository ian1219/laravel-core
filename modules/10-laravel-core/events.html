In one sentence

An event announces that something happened ("a post was published"), and any number of listeners can react to it without the original code knowing they exist.

📻It's like a radio broadcast. The station announces the news once. Whoever has tuned in reacts in their own way, and the station doesn't need a list of listeners or care how many there are.

Why it matters

Side effects without the spaghetti

🧩

Decoupled code

Publishing a post shouldn't need to know about emails, sitemaps and analytics. Each reaction lives in its own small class.

➕

Add features safely

New reaction? Write a new listener. You never touch the working code that fires the event.

⚡

Faster responses

Slow listeners (like emailing 1,000 subscribers) can run on a queue, so the user isn't kept waiting.

The big picture

One event, many listeners

Event
A simple class describing what happened, carrying the relevant data (e.g. the Post). Named in the past tense.
Listener
A class with a handle() method that reacts to one event.
Dispatch
Firing an event so its listeners run.
Step by step

Fire your first event

  1. Create the event

    
          php artisan make:event PostPublished

    An event is just a data container. Use a promoted constructor property for the post:

    
          <?php

          namespace App\Events;

          use App\Models\Post;
          use Illuminate\Foundation\Events\Dispatchable;
          use Illuminate\Queue\SerializesModels;

          class PostPublished
          {
              use Dispatchable, SerializesModels;

              public function __construct(public Post $post) {}
          }

    SerializesModels stores just the post's ID when the event is queued, and re-fetches the fresh model later.

  2. Create a listener (auto-discovered)

    
          php artisan make:listener RefreshSitemap --event=PostPublished
        
    
          use App\Events\PostPublished;

          class RefreshSitemap
          {
              public function handle(PostPublished $event): void
              {
                  Cache::forget('sitemap.xml');   // rebuilt on next visit
              }
          }

    There's no registration step. Laravel's event discovery scans app/Listeners and connects each listener to the event type-hinted in its handle() method. Check the wiring with:

    
          php artisan event:list
    ℹ️ Registering manually

    Listeners outside app/Listeners, or closures, can be registered in AppServiceProvider::boot() with Event::listen(PostPublished::class, RefreshSitemap::class). In production, run php artisan event:cache (part of optimize) so discovery doesn't rescan on every request.

  3. Dispatch the event

    Fire it where the thing actually happens. Both forms are equivalent:

    
          public function publish(Post $post): void
          {
              $post->update(['published_at' => now()]);

              PostPublished::dispatch($post);      // via the Dispatchable trait
              // event(new PostPublished($post));  // helper, same result
          }

    Your service is now done. Emails, sitemaps and logs are the listeners' business.

  4. Queue slow listeners with ShouldQueue

    Emailing every subscriber is slow. Implement ShouldQueue and the listener is pushed to the queue instead of running during the request:

    
          use Illuminate\Contracts\Queue\ShouldQueue;
          use Illuminate\Queue\InteractsWithQueue;

          class NotifySubscribers implements ShouldQueue
          {
              use InteractsWithQueue;

              public $tries = 3;

              public function handle(PostPublished $event): void
              {
                  $event->post->author->subscribers->each->notify(
                      new NewPostNotification($event->post)
                  );
              }
          }

    A queue worker (php artisan queue:work) must be running for queued listeners to execute.

  5. Model events and observers

    Eloquent fires its own events automatically as models change: creating, created, updating, updated, saving, saved, deleting, deleted and more. An observer groups your reactions to one model:

    
          php artisan make:observer PostObserver --model=Post
        
    
          class PostObserver
          {
              public function creating(Post $post): void
              {
                  $post->slug ??= Str::slug($post->title);
              }

              public function deleted(Post $post): void
              {
                  $post->comments()->delete();
              }
          }

    Attach it to the model with the ObservedBy attribute:

    
          use App\Observers\PostObserver;
          use Illuminate\Database\Eloquent\Attributes\ObservedBy;

          #[ObservedBy([PostObserver::class])]
          class Post extends Model
          {
              // ...
          }
    ⚠️ Mass queries skip model events

    Post::where(...)->update([...]) and ->delete() on a query run straight SQL. No models are loaded, so no model events fire.

Common mistakes

Avoid this, do that

❌ Avoid

          $post->update(['published_at' => now()]);
          $this->mailer->notifySubscribers($post);
          $this->sitemap->add($post);
          $this->search->index($post);
          $this->slack->announce($post);

Every new side effect means editing this method and injecting another dependency.

✅ Do

          $post->update(['published_at' => now()]);
          PostPublished::dispatch($post);

Announce once; each side effect becomes its own listener that you can add, remove or queue independently.

❌ Avoid

          // Core logic hidden in a listener
          class ChargeCustomer
          {
              public function handle(OrderPlaced $e) { ... }
          }

If the step must happen for the action to succeed, hiding it in a listener makes the flow hard to follow.

✅ Do

          $payment = $this->gateway->charge($order);
          OrderPlaced::dispatch($order);

Call essential steps directly; use events for optional reactions that can happen around it.

💡 Pro tip: when do events beat direct calls?
  • Use an event when several independent things react, when reactions may grow over time, or when they can run later on a queue.
  • Call directly when there's one essential step, when you need its return value, or when readers must see the flow top to bottom.
  • In tests, Event::fake() stops listeners running and lets you Event::assertDispatched(PostPublished::class).
🏋️ Try it yourself
  1. Create a CommentPosted event that carries a Comment.
  2. Create a NotifyPostAuthor listener for it that writes to the log, and confirm it appears in php artisan event:list.
  3. Dispatch the event from your comment controller's store() method and check storage/logs/laravel.log.
  4. Make the listener implement ShouldQueue, set QUEUE_CONNECTION=database, and run php artisan queue:work to see it processed.
  5. Add a PostObserver that fills in the slug on creating.
Recap

Key takeaways

  • Events say what happened; listeners decide what to do about it.
  • make:event and make:listener --event= generate the classes; listeners in app/Listeners are auto-discovered.
  • Dispatch with PostPublished::dispatch($post) or event(new PostPublished($post)).
  • Implement ShouldQueue to move slow listeners to the queue.
  • Eloquent fires model events; observers group them, attached with #[ObservedBy].
  • Use events for optional, growing side effects; call essential steps directly.
