In one sentence

Every request enters through public/index.php, boots the application, travels through the kernel, router and middleware to your controller, and comes back out as a response.

📦Think of a parcel at a sorting centre. It arrives at one loading dock, gets scanned, passes several checkpoints, reaches the right desk to be handled, and leaves through the same building as a reply, while the staff tidy up afterwards.

The big picture

One request, top to bottom

Let's follow POST /posts (saving a new blog post) through a Laravel 11+ app.

Step by step

Walk through the real files

  1. The entry point: public/index.php

    Your web server (Nginx, Apache or php artisan serve) is configured to send every request to this one file. It's short, and you'll never need to edit it:

    
          <?php

          use Illuminate\Foundation\Application;
          use Illuminate\Http\Request;

          define('LARAVEL_START', microtime(true));

          // Maintenance mode? (php artisan down)
          if (file_exists($maintenance = __DIR__.'/../storage/framework/maintenance.php')) {
              require $maintenance;
          }

          require __DIR__.'/../vendor/autoload.php';

          /** @var Application $app */
          $app = require_once __DIR__.'/../bootstrap/app.php';

          $app->handleRequest(Request::capture());

    Three jobs: load Composer's autoloader, build the application, and hand it the incoming request. Request::capture() turns PHP's raw $_GET, $_POST, cookies and headers into one Illuminate\Http\Request object.

  2. Building the app: bootstrap/app.php

    This file creates the application instance, which is the service container (Application extends Container). It also records your configuration:

    
          return Application::configure(basePath: dirname(__DIR__))
              ->withRouting(
                  web: __DIR__.'/../routes/web.php',
                  commands: __DIR__.'/../routes/console.php',
                  health: '/up',
              )
              ->withMiddleware(function (Middleware $middleware): void {
                  //
              })
              ->withExceptions(function (Exceptions $exceptions): void {
                  //
              })->create();

    Nothing has handled the request yet. We've only built the machine.

  3. The HTTP kernel boots the app

    handleRequest() resolves the HTTP kernel (Illuminate\Foundation\Http\Kernel) from the container and calls its handle() method. Before touching your routes, the kernel runs a list of bootstrappers, in this order:

    BootstrapperWhat it does
    LoadEnvironmentVariablesReads your .env file
    LoadConfigurationLoads every file in config/
    HandleExceptionsSets up error and exception handling
    RegisterFacadesMakes facades work
    RegisterProvidersCalls register() on every service provider
    BootProvidersCalls boot() on every service provider

    All of them live in Illuminate\Foundation\Bootstrap. This is the moment your AppServiceProvider runs: it's the most important step of the whole boot.

  4. Middleware, router, controller

    Now the kernel sends the request through the global middleware using a Pipeline (the onion from the Middleware lesson). At the centre of that pipeline sits the router:

    1. Router::dispatch() finds the route matching the method and URL (or throws a 404).
    2. The route's own middleware (web group, auth…) runs through a second pipeline.
    3. The controller is resolved from the container, so its constructor dependencies and method arguments (like StorePostRequest $request) are injected.
    
          public function store(StorePostRequest $request, PostPublisher $publisher)
          {
              $post = $request->user()->posts()->create($request->validated());
              $publisher->publish($post);

              return redirect()->route('posts.show', $post);
          }

  5. Response, send, terminate

    Whatever the controller returns (a view, an array, a model, a redirect) is converted by Router::toResponse() into a proper response object. Arrays and models become JSON, strings become HTML.

    The response travels back out through every middleware layer, then ->send() writes headers and body to the browser. Finally $kernel->terminate() runs any work that should happen after the user already has their page:

    
          public function handle(Request $request, Closure $next): Response
          {
              return $next($request);
          }

          // Runs after the response was sent (on PHP-FPM)
          public function terminate(Request $request, Response $response): void
          {
              Log::info('Request took '.round(microtime(true) - LARAVEL_START, 3).'s');
          }
    ℹ️ Exceptions are part of the lifecycle too

    If anything throws (a 404, a failed validation, a bug), the kernel catches it and passes it to the exception handler you configured in ->withExceptions(). It turns the exception into an error page or JSON response, which then flows out like any other response.

Common mistakes

Avoid this, do that

❌ Avoid

          // AppServiceProvider::boot()
          View::share('user', auth()->user());

Providers boot before the session middleware runs, so the user isn't loaded yet and this is always null.

✅ Do

          // AppServiceProvider::boot()
          View::composer('*', fn ($view) =>
              $view->with('user', auth()->user())
          );

A view composer runs later, when the view renders, after middleware has started the session.

❌ Avoid

          // public/index.php
          ini_set('memory_limit', '1G');
          $app->handleRequest(Request::capture());

Editing framework entry files makes upgrades painful, and your changes are easily lost.

✅ Do

          // bootstrap/app.php, a provider, or middleware
          ->withMiddleware(...)

Use the extension points Laravel gives you: bootstrap/app.php, providers and middleware.

💡 Pro tip: read the source

Open vendor/laravel/framework/src/Illuminate/Foundation/Http/Kernel.php and find sendRequestThroughRouter(). It's only a few lines, and you'll recognise every step from this page.

🏋️ Try it yourself
  1. Open public/index.php and bootstrap/app.php in your project and match each line to a box in the diagram.
  2. Add Log::info('provider booted') in AppServiceProvider::boot() and Log::info('controller ran') in a controller. Load the page and check the order in storage/logs/laravel.log.
  3. Write a middleware with both handle() and terminate() that logs a message from each. Register it globally and confirm which logs first.
  4. Run php artisan down, visit the site, then php artisan up. Which line of index.php handled that?
Recap

Key takeaways

  • Every request enters through public/index.php.
  • bootstrap/app.php builds the Application, which is the service container.
  • The HTTP kernel runs bootstrappers: env, config, exceptions, facades, then providers (register → boot).
  • Global middleware → router → route middleware → controller, all via pipelines.
  • The response flows back out through middleware, is sent, then terminate() runs.
