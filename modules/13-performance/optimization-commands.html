In one sentence

In production, Laravel can pre-compile its config, routes, views and events into fast cached files, so each request skips work that only needs doing once per deploy.

🧳It's like packing your suitcase the night before a trip. Instead of searching every drawer each morning, everything you need is already folded in one place, ready to grab.

Why it matters

Free speed, and fewer surprises

🚀

Faster every request

Laravel stops re-reading dozens of config files and route definitions on every single hit.

🔒

Safer errors

APP_DEBUG=false hides stack traces, file paths and environment values from visitors.

📋

Repeatable deploys

A short checklist you run every time means production behaves the same after every release.

Step by step

A production deploy, in order

  1. Set production environment values

    Before anything else, the server's .env must say it's production and must not show debug pages.

    
          APP_ENV=production
          APP_DEBUG=false
          APP_URL=https://blog.example.com
          LOG_LEVEL=warning
    ⚠️ APP_DEBUG=true in production is a security hole

    Debug error pages can reveal source code, file paths, database queries and environment variables to anyone who triggers an error.

  2. Install dependencies the production way

    
          composer install --optimize-autoloader --no-dev
    • --no-dev skips development-only packages like Debugbar, Pest/PHPUnit and Faker.
    • --optimize-autoloader builds a classmap, a ready-made list of where every class lives, so PHP doesn't have to search folders.

    Build your frontend assets too, typically with npm ci && npm run build.

  3. Migrate, then cache everything with optimize

    
          php artisan migrate --force
          php artisan optimize

    --force confirms you really mean to migrate in production. php artisan optimize runs all of these for you:

    CommandWhat it doesClear with
    config:cacheMerges all config into one fileconfig:clear
    route:cachePre-compiles route registrationroute:clear
    view:cacheCompiles every Blade view ahead of timeview:clear
    event:cacheSaves the event/listener mapevent:clear

    To undo all of them at once: php artisan optimize:clear.

  4. Understand the config cache gotcha

    After config:cache, the .env file is not loaded anymore. Values are read from the cached config file. So calling env() outside a config file returns null.

    
          'newsletter' => [
              'key' => env('NEWSLETTER_KEY'),   // ✅ env() only inside config files
          ],
        
    
          $key = config('services.newsletter.key');   // ✅ everywhere else

    Also, after changing .env or any config on the server, re-run php artisan config:cache (or optimize) or the change won't take effect.

  5. Restart workers and enable OPcache

    
          php artisan queue:restart

    Long-running queue workers keep old code in memory until restarted.

    OPcache is a PHP extension that stores compiled PHP in memory, so files aren't re-parsed on each request. It's often the single biggest win. Make sure it's enabled in your server's php.ini:

    
          opcache.enable=1
          opcache.memory_consumption=256
          opcache.max_accelerated_files=20000
          opcache.validate_timestamps=0   ; fastest; restart PHP-FPM on each deploy

    With validate_timestamps=0, PHP never checks for changed files, so reload PHP-FPM as part of every deploy.

The production checklist

  • APP_ENV=production and APP_DEBUG=false
  • APP_KEY set (and backed up somewhere safe)
  • composer install --optimize-autoloader --no-dev
  • npm ci && npm run build
  • php artisan migrate --force
  • php artisan optimize (config, route, view and event caches)
  • php artisan queue:restart
  • OPcache enabled; PHP-FPM reloaded
  • Cache and queue on a shared store (database or Redis) if you run several servers
  • Scheduler cron set up: * * * * * php artisan schedule:run

      php artisan down
      git pull origin main
      composer install --optimize-autoloader --no-dev
      npm ci && npm run build
      php artisan migrate --force
      php artisan optimize
      php artisan queue:restart
      php artisan up

Hosting tools like Laravel Cloud and Laravel Forge run a script like this for you on every push.

Common mistakes

Avoid this, do that

❌ Avoid

          // in a controller
          $key = env('NEWSLETTER_KEY');

Returns null once the config is cached, so it works locally and breaks in production.

✅ Do

          $key = config('services.newsletter.key');

Read env() only in config/*.php, and use config() everywhere else.

❌ Avoid

          # on your laptop, during development
          php artisan optimize

Then you edit a route or config value and nothing changes, because the cached copy is used.

✅ Do

          php artisan optimize:clear

Keep caches for production. Locally, clear them if something seems “stuck”.

💡 Pro tip: check your setup at a glance

php artisan about shows your environment, debug mode, cache drivers and whether config, routes, views and events are cached.

🏋️ Try it yourself
  1. Run php artisan about and note the “Cache” section.
  2. Run php artisan optimize, then about again. Find the new files in bootstrap/cache.
  3. Add a test route, refresh the browser and notice it's missing. Run php artisan optimize:clear and try again.
  4. Search your app/ folder for env( and move any matches into a config file.
  5. Write your own deploy.sh based on the checklist above.
Recap

Key takeaways

  • php artisan optimize runs config:cache, route:cache, view:cache and event:cache.
  • composer install --optimize-autoloader --no-dev gives a fast autoloader without dev packages.
  • Always set APP_DEBUG=false in production.
  • After config:cache, env() only works inside config files: use config() in your code.
  • Enable OPcache, restart queue workers, and use optimize:clear when caches get in the way.
