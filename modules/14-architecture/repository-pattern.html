In one sentence

A repository is a class that hides where and how data is stored behind an interface, so the rest of your app just asks for “published posts” without knowing about SQL or Eloquent.

📚A library desk: you ask the librarian for “books by Ada Lovelace” and get them, without knowing whether they came from the shelf, the basement or another branch. Useful in a huge library system, but overkill if the books are on one shelf right behind you.

Why it matters

A famous pattern, often misused

🔌

Swappable data sources

When data might come from Eloquent today and an external API tomorrow, an interface lets you swap the source without touching callers.

🎯

One home for complex queries

Big reporting or search queries get a named method (topAuthorsThisMonth()) instead of being copy-pasted.

⚖️

But it has a cost

Eloquent is already an abstraction over the database. Adding another layer on top is often extra code for little gain.

The big picture

Where a repository sits

This builds on two ideas you already know: interfaces and binding an interface to a class in the service container.

SituationRepository?Why
Typical CRUD app on one database❌ Usually notEloquent, scopes and services already cover it
Same query copy-pasted in 5 places🤔 MaybeA query scope or service method is often enough
Data from an external API or several sources✅ YesThe interface hides very different implementations

Your team already uses it consistently✅ Follow itConsistency beats personal taste
Step by step

Build a repository (then judge it)

We'll build one properly, so you can recognise it in other codebases and decide when it's worth it.

  1. Start from the “before”

    This controller builds a query inline. It's perfectly fine on its own. It becomes a problem only if the same query appears in many places.

    
          public function index()
          {
              $posts = Post::query()
                  ->whereNotNull('published_at')
                  ->where('published_at', '<=', now())
                  ->with('author')
                  ->latest('published_at')
                  ->paginate(10);

              return view('posts.index', compact('posts'));
          }

  2. Try the lighter fix first: a query scope

    A local scope names a reusable query piece right on the model. For most apps, this solves the duplication without any new layer.

    
          use Illuminate\Database\Eloquent\Builder;

          public function scopePublished(Builder $query): void
          {
              $query->whereNotNull('published_at')
                    ->where('published_at', '<=', now());
          }

          // Usage: Post::published()->latest('published_at')->paginate(10);

  3. Define the contract

    If you really need a repository, start with an interface. It lists what callers may ask for, in business words.

    
          <?php

          namespace App\Repositories;

          use App\Models\Post;
          use Illuminate\Contracts\Pagination\LengthAwarePaginator;

          interface PostRepository
          {
              public function publishedPaginated(int $perPage = 10): LengthAwarePaginator;

              public function findBySlug(string $slug): ?Post;
          }

  4. Write the Eloquent implementation

    The implementation is where Eloquent lives. Callers never see this class directly.

    
          <?php

          namespace App\Repositories;

          use App\Models\Post;
          use Illuminate\Contracts\Pagination\LengthAwarePaginator;

          class EloquentPostRepository implements PostRepository
          {
              public function publishedPaginated(int $perPage = 10): LengthAwarePaginator
              {
                  return Post::published()->with('author')
                      ->latest('published_at')->paginate($perPage);
              }

              public function findBySlug(string $slug): ?Post
              {
                  return Post::published()->where('slug', $slug)->first();
              }
          }

  5. Bind it in a service provider and inject it

    Tell the container: “when someone asks for PostRepository, give them EloquentPostRepository”.

    
          public function register(): void
          {
              $this->app->bind(
                  \App\Repositories\PostRepository::class,
                  \App\Repositories\EloquentPostRepository::class,
              );
          }
        
    
          public function __construct(private PostRepository $posts) {}

          public function index()
          {
              return view('posts.index', [
                  'posts' => $this->posts->publishedPaginated(),
              ]);
          }

  6. Honestly weigh the result

    You now have 3 files instead of 1, and every new query means editing an interface and a class. In return, you can swap the implementation (for example a CachedPostRepository or an ApiPostRepository) by changing one binding.

    ⚠️ “We'll switch databases one day” is rarely true

    Eloquent already works across MySQL, PostgreSQL, SQLite and SQL Server. And repositories that return Eloquent models (as most Laravel ones do) don't really hide Eloquent anyway. Add the layer for a concrete reason, not “just in case”.

    For tests, you rarely need a fake repository either: Laravel's factories plus RefreshDatabase on SQLite make real-database tests fast.

Common mistakes

Avoid this, do that

❌ Avoid

          interface PostRepository {
              public function all();
              public function find($id);
              public function create(array $data);
              public function update($id, array $data);
          }

A generic CRUD repository just renames Eloquent methods and hides features like eager loading and scopes.

✅ Do

          interface PostRepository {
              public function publishedPaginated(int $perPage = 10): LengthAwarePaginator;
              public function trendingThisWeek(int $limit): Collection;
          }

If you build one, give it intention-revealing methods that hold real query knowledge.

❌ Avoid

          // Repository used in one place,
          // for one query, with one implementation
          $this->posts->latestFive();

An interface with a single implementation and a single caller is pure ceremony.

✅ Do

          Post::published()->latest()->take(5)->get();

Use a scope or plain Eloquent until a real need for abstraction appears.

💡 Pro tip: the upgrade path is cheap

Start with scopes and service classes. If you later need a repository, you can extract one in an afternoon, because your queries are already named and grouped. Adding it too early costs you on every feature; adding it late costs you once.

🏋️ Try it yourself
  1. Add a scopePublished() to your Post model and replace every inline “published” query with it.
  2. Create a PostRepository interface and an EloquentPostRepository with publishedPaginated(), and bind them in AppServiceProvider.
  3. Write a second implementation, CachedPostRepository, that wraps the Eloquent one with Cache::remember(). Switch the binding and confirm the controller didn't change.
  4. Write two sentences on whether your project actually needs the repository. Be honest!
Recap

Key takeaways

  • A repository hides data access behind an interface; callers depend on the contract, not the storage.
  • Bind the interface to an implementation in a service provider with $this->app->bind().
  • Eloquent is already an abstraction, so for typical CRUD apps a repository is usually unnecessary.
  • Reach for scopes and service classes first; they solve most duplication.
  • Repositories earn their keep with multiple data sources, external APIs, or framework-free domain code.
  • If you use one, prefer intention-revealing methods over generic all()/find()/create().
