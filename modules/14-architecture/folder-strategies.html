In one sentence

As an app grows, you can keep Laravel's default “group by type” folders, or switch to grouping code by business area (domains) or by self-contained modules.

🏬A small shop can sort stock by type: all boxes on one shelf, all bottles on another. A department store sorts by department instead (kitchen, garden, toys), each with its own boxes and bottles. Neither is “right”; it depends on how big the store is.

Why it matters

Structure decides how fast you find things

🧭

Navigation

With 200 models in one app/Models folder, finding everything about “billing” means searching five folders.

👥

Team ownership

Grouping by business area lets one team own Billing while another owns Catalog, with fewer merge conflicts.

💸

Restructuring costs

Moving hundreds of files later is painful. Choosing sensibly early (and not over-engineering) saves real time.

The big picture

Three ways to slice the same app

We'll use one running example: a blog with posts, comments and a paid billing area for premium subscriptions.

Step by step

Tour each structure

  1. The default structure: group by type

    This is what laravel new gives you (see Directory Structure). Every controller is in one folder, every model in another. Add Services, Actions and Data folders as you learned earlier in this module.

    app/
├── Actions/
│   ├── PublishPost.php
│   └── StartSubscription.php
├── Http/
│   ├── Controllers/
│   │   ├── PostController.php
│   │   ├── CommentController.php
│   │   └── SubscriptionController.php
│   └── Requests/
├── Models/
│   ├── Post.php
│   ├── Comment.php
│   ├── Subscription.php
│   └── Invoice.php
├── Policies/
└── Services/
    └── InvoiceService.php   ← billing logic lives far from billing models

    Great for: small and medium apps, solo developers, and anyone still learning. Every Laravel tutorial and package assumes it, and the make:* commands put files here automatically.

  2. Domain-based structure: group logic by business area

    A domain is one area of the business (Billing, Blog, Users). Business code (models, actions, DTOs, events) moves into app/Domain/<Area>, while HTTP code often stays in app/Http.

    app/
├── Domain/
│   ├── Billing/
│   │   ├── Actions/
│   │   │   ├── StartSubscription.php
│   │   │   └── IssueInvoice.php
│   │   ├── Data/
│   │   │   └── SubscriptionData.php
│   │   ├── Events/
│   │   │   └── SubscriptionStarted.php
│   │   └── Models/
│   │       ├── Subscription.php
│   │       └── Invoice.php
│   └── Blog/
│       ├── Actions/
│       │   └── PublishPost.php
│       └── Models/
│           ├── Post.php
│           └── Comment.php
├── Http/               ← controllers & requests stay here
│   └── Controllers/
│       ├── Billing/SubscriptionController.php
│       └── Blog/PostController.php
└── Models/
    └── User.php             ← shared by every domain

    Namespaces follow folders, so a model becomes App\Domain\Billing\Models\Invoice. No extra Composer setup is needed, because everything is still under App\.

    
          <?php

          namespace App\Domain\Billing\Actions;

          use App\Domain\Billing\Data\SubscriptionData;
          use App\Domain\Billing\Models\Subscription;
          use App\Models\User;

          class StartSubscription
          {
              public function handle(User $user, SubscriptionData $data): Subscription
              {
                  // ...
              }
          }

  3. Teach Laravel where moved files live

    Some conventions are based on folder names. When models leave app/Models, check these spots:

    • Factories: add a newFactory() method to the model, or customise Factory::guessFactoryNamesUsing().
    • Policies: auto-discovery looks for Policies next to Models. Register others with Gate::policy() in a service provider.
    • Generators: pass a full path, such as php artisan make:model Domain/Billing/Models/Invoice.
    
          use Database\Factories\InvoiceFactory;

          protected static function newFactory(): InvoiceFactory
          {
              return InvoiceFactory::new();
          }

  4. Modular structure: mini-apps inside your app

    A module goes further: it bundles everything for one area, including routes, views, migrations and tests, plus its own service provider. Modules usually live outside app/, with their own namespace.

    modules/
├── Billing/
│   ├── database/
│   │   └── migrations/
│   ├── resources/
│   │   └── views/
│   ├── routes/
│   │   └── web.php
│   ├── src/
│   │   ├── Actions/
│   │   ├── Http/Controllers/
│   │   ├── Models/
│   │   └── BillingServiceProvider.php  ← loads routes, views, migrations
│   └── tests/
└── Blog/
    └── … same shape …

    Composer needs to know the new namespace, and the module's provider must be registered:

    
          "autoload": {
              "psr-4": {
                  "App\\": "app/",
                  "Modules\\Billing\\": "modules/Billing/src/"
              }
          }
        
    
          public function boot(): void
          {
              $this->loadRoutesFrom(__DIR__.'/../routes/web.php');
              $this->loadViewsFrom(__DIR__.'/../resources/views', 'billing');
              $this->loadMigrationsFrom(__DIR__.'/../database/migrations');
          }

    Run composer dump-autoload and add the provider to bootstrap/providers.php. Views are then referenced as view('billing::invoices.index').

  5. Choose with a decision table

    Be honest about your app's size and team. Most apps should start with the default and evolve only when the pain is real.

    QuestionDefaultDomain-basedModular
    Team size1–3 devs3–10 devsSeveral teams
    App sizeUp to ~30 modelsMany models in clear areasLarge, with near-independent areas
    Setup effortNoneLow (namespaces, factories)Higher (Composer, providers, conventions)
    Fits tutorials & generators✅ Perfectly🟡 Mostly🟠 Needs extra work
    Clear ownership of areas🟠 Weak✅ Good✅ Strongest
    Could split into a separate service later🟠 Hard🟡 Possible✅ Easiest
    Best forLearning, MVPs, most appsGrowing productsBig platforms, many teams
    ℹ️ You can mix approaches

    A common, practical path: start with the default, add app/Actions and app/Data, then group those by area (app/Actions/Billing) as the app grows. Move to full domains only when an area clearly stands on its own.

Common mistakes

Avoid this, do that

❌ Avoid
modules/
└── Todo/   ← 1 model, 4 routes
    ├── src/
    ├── routes/
    └── database/

A full modular setup for a weekend project adds files and conventions you'll fight on every feature.

✅ Do
app/
├── Http/Controllers/TodoController.php
└── Models/Todo.php

Start with Laravel's defaults. Restructure when navigation actually hurts.

❌ Avoid

          // Inside the Blog domain
          use App\Domain\Billing\Models\Invoice;

          $post->author->invoices()->latest()->first()->markPaid();

Reaching deep into another domain's models recreates the tangle you were trying to avoid.

✅ Do

          // Blog talks to Billing through an action or event
          app(MarkLatestInvoicePaid::class)->handle($user);
          // or: event(new PostSponsored($post));

Cross area boundaries through a small public surface (actions, events), not raw internals.

💡 Pro tip: consistency beats cleverness

Whatever structure you choose, write it down in the README (“actions live in app/Domain/<Area>/Actions”). A slightly imperfect structure everyone follows beats a perfect one nobody understands.

🏋️ Try it yourself
  1. Draw your current project's app/ folder as a tree and circle the files that belong to one business area.
  2. In a test project, move Invoice to app/Domain/Billing/Models, fix the namespace and add newFactory(). Run your tests.
  3. Create modules/Billing with a service provider that loads one route returning “Billing works”. Register it and visit the URL.
  4. Fill in the decision table for your own project and decide which structure you'd pick, in one sentence.
Recap

Key takeaways

  • Laravel's default structure groups by type and is the right choice for most apps.
  • Domain-based structure groups business code by area under app/Domain/<Area>.
  • Modular structure bundles routes, views, migrations and code per area, with its own provider and namespace.
  • Moving models means fixing namespaces, factories and policy registration.
  • Areas should talk through actions and events, not each other's internals.
  • Choose by team and app size, document the choice, and evolve gradually.
