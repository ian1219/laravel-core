In one sentence

Roles group users (admin, editor, author), and permissions name individual actions (“publish posts”), so your gates and policies can check what someone is instead of who they are.

🏥In a hospital, nobody keeps a list of which doctor may open which cupboard. Staff have roles (nurse, surgeon, cleaner), and each role comes with a set of key cards. Hire a new nurse, give them the nurse role, and they get every key a nurse needs.

Why it matters

From “is it mine?” to “what's my job?”

👥

Teams, not just owners

Editors need to fix other people's posts. Ownership checks alone can't express that.

⚙️

Change access without deploys

When roles live in the database, an admin can promote someone with a click instead of a code change.

📏

Start simple, scale later

A single column is enough at first. Knowing the next step means you won't paint yourself into a corner.

Step by step

Grow a role system for the blog

  1. Start with a role column and an enum

    A PHP enum lists the allowed values, so a typo like 'admn' can't sneak in. Add the column with a migration and cast it on the model.

    
          <?php

          namespace App\Enums;

          enum Role: string
          {
              case Admin = 'admin';
              case Editor = 'editor';
              case Author = 'author';
          }
        
    
          Schema::table('users', function (Blueprint $table) {
              $table->string('role')->default('author');
          });
        
    
          protected function casts(): array
          {
              return [
                  'email_verified_at' => 'datetime',
                  'password' => 'hashed',
                  'role' => \App\Enums\Role::class,
              ];
          }

  2. Use the role in policies and gates

    Combine roles with ownership: editors can update any post, and authors can only update their own.

    
          use App\Enums\Role;

          public function before(User $user, string $ability): ?bool
          {
              return $user->role === Role::Admin ? true : null;
          }

          public function update(User $user, Post $post): bool
          {
              return $user->role === Role::Editor
                  || $user->id === $post->user_id;
          }

    Remember to keep the role column out of $fillable, so nobody can promote themselves through a form (see mass assignment).

  3. Outgrown one role? Design roles & permissions tables

    When users need several roles, or admins want to edit what each role can do, move to two many-to-many relationships (see Relationships).

    
          public function roles(): BelongsToMany
          {
              return $this->belongsToMany(Role::class);
          }

          public function hasPermission(string $name): bool
          {
              return $this->roles()
                  ->whereHas('permissions', fn ($q) => $q->where('name', $name))
                  ->exists();
          }

    Here Role is an Eloquent model (not the enum from step 1), with its own permissions() belongsToMany relationship.

  4. Plug permissions into gates

    One Gate::before can route every ability name to the permissions table, so @can('publish posts') just works.

    
          Gate::before(function (User $user, string $ability) {
              return $user->hasPermission($ability) ? true : null;
          });
    ⚠️ Watch your queries

    This runs a database query on every check. A page with twenty @can calls makes twenty queries. Real implementations cache the user's permissions, and that's one big reason to use a package.

  5. Reach for spatie/laravel-permission

    When you need multiple roles, permissions editable at runtime, caching and route middleware, use the popular spatie/laravel-permission package. It implements exactly the table design above.

    
          composer require spatie/laravel-permission
          php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider"
          php artisan migrate
        
    
          use Spatie\Permission\Traits\HasRoles;   // add `use HasRoles;` to User

          // set up (e.g. in a seeder)
          $editor = Role::create(['name' => 'editor']);
          Permission::create(['name' => 'publish posts']);
          $editor->givePermissionTo('publish posts');

          // use it
          $user->assignRole('editor');
          $user->hasRole('editor');          // true
          $user->can('publish posts');       // true, works with Gate and @can
        
    
          @role('editor')
              <a href="/admin/review">Review queue</a>
          @endrole

          @can('publish posts') <button>Publish</button> @endcan

    To use its role: and permission: route middleware, register the aliases in bootstrap/app.php with $middleware->alias([...]), as described in the package docs.

Common mistakes

Avoid this, do that

❌ Avoid

          @if (auth()->user()->role === 'admin'
              || auth()->user()->role === 'editor')
              <button>Publish</button>
          @endif

Role checks scattered through views are hard to find and easy to get wrong when a new role appears.

✅ Do

          @can('publish', $post)
              <button>Publish</button>
          @endcan

Views ask about abilities. Which roles have those abilities is decided in one policy or gate.

❌ Avoid

          protected $fillable = ['name', 'email', 'password', 'role'];

A crafted form field role=admin could promote any user who edits their profile.

✅ Do

          protected $fillable = ['name', 'email', 'password'];
          // $user->role = Role::Editor; $user->save();  (admin only)

Set roles explicitly in admin-only code paths, never through mass assignment.

💡 Pro tip: check permissions, not roles

Prefer can('publish posts') over hasRole('editor'). If a “senior author” role later needs to publish too, you add a permission to that role and change zero lines of code.

Recap

Key takeaways

  • Roles group users, and permissions name actions. Roles hold permissions.
  • Small apps: a role column cast to a PHP enum is plenty.
  • Larger apps: roles, permissions and two pivot tables (many-to-many).
  • spatie/laravel-permission gives you that design with caching, middleware and Blade directives.
  • Keep checks in policies/gates, ask about abilities in views, and never mass-assign roles.
