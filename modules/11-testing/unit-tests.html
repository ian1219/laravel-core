In one sentence

A unit test checks one small piece of logic, usually a single class or method, on its own, without HTTP, a database or the rest of the app.

🔩A car factory tests each part before assembly: does this spark plug spark? It's quick, cheap, and if it fails you know exactly which part is faulty, long before the whole car refuses to start.

Why it matters

Small, fast, precise

⚡

Blazing fast

No database or HTTP means thousands of unit tests can run in about a second.

🎯

Pinpoints the bug

When a unit test fails, only one small class could be at fault.

🧼

Encourages clean code

Code that's easy to unit test is usually small, focused and loosely coupled.

Step by step

Unit test a reading-time calculator

Our blog wants to show "3 min read" on each post. That logic deserves its own small class.

  1. Write a plain PHP class

    Pure logic like this doesn't need Eloquent or facades. It takes input and returns output, which makes it perfect for unit testing.

    
          <?php

          namespace App\Support;

          class ReadingTime
          {
              public function __construct(private int $wordsPerMinute = 200) {}

              public function minutes(string $text): int
              {
                  $words = str_word_count(strip_tags($text));

                  return max(1, (int) ceil($words / $this->wordsPerMinute));
              }
          }

  2. Generate a unit test

    The --unit flag puts the file in tests/Unit. Unit tests there don't boot the Laravel app, which keeps them very fast.

    
          php artisan make:test ReadingTimeTest --unit

  3. Arrange, act, assert with expect()

    Pest's expect() API reads like English: expect this value to be 3.

    
          <?php

          use App\Support\ReadingTime;

          it('rounds up to the next whole minute', function () {
              // Arrange
              $calculator = new ReadingTime(wordsPerMinute: 200);
              $text = str_repeat('word ', 450);

              // Act
              $minutes = $calculator->minutes($text);

              // Assert
              expect($minutes)->toBe(3);
          });

          it('never returns less than one minute', function () {
              expect((new ReadingTime)->minutes(''))->toBe(1);
          });

    Other handy expectations: toBeTrue(), toEqual(), toContain(), toHaveCount(), toBeInstanceOf(), and toThrow().

  4. Test many inputs at once with datasets

    A dataset runs the same test with different values. Each row is reported as its own test.

    
          it('calculates minutes for different lengths', function (int $words, int $expected) {
              $text = str_repeat('word ', $words);

              expect((new ReadingTime)->minutes($text))->toBe($expected);
          })->with([
              'short'   => [50, 1],
              'exact'   => [400, 2],
              'just over' => [401, 3],
          ]);

  5. The PHPUnit equivalent

    In PHPUnit, the same test is a class extending PHPUnit\Framework\TestCase, with $this->assert… methods.

    
          use App\Support\ReadingTime;
          use PHPUnit\Framework\TestCase;

          class ReadingTimeTest extends TestCase
          {
              public function test_it_rounds_up_to_the_next_minute(): void
              {
                  $minutes = (new ReadingTime(200))->minutes(str_repeat('word ', 450));

                  $this->assertSame(3, $minutes);
              }
          }

  6. Use it from the app, test it in isolation

    The model can use the class, but the logic stays tested on its own. A feature test only needs to check that "3 min read" appears on the page.

    
          public function readingTime(): int
          {
              return (new ReadingTime)->minutes($this->body);
          }
    ℹ️ Need Laravel helpers in a unit test?

    Tests in tests/Unit don't boot the framework, so facades, config() and the database aren't available. If you need them, it's really a feature test, so move it to tests/Feature.

Common mistakes

Avoid this, do that

❌ Avoid

          public function store(Request $request)
          {
              $minutes = max(1, ceil(
                  str_word_count($request->body) / 200));
              // ...
          }

Logic buried in a controller can only be tested through a full HTTP request.

✅ Do

          $minutes = (new ReadingTime)
              ->minutes($request->body);

Extract it into a small class, then unit test that class directly.

❌ Avoid

          expect($minutes)->toBeGreaterThan(0);

A vague assertion passes even when the calculation is wrong.

✅ Do

          expect($minutes)->toBe(3);

Assert the exact expected value for a known input.

💡 Pro tip: test the edges

Bugs hide at the boundaries: empty strings, zero, exactly 200 words, 201 words, negative numbers. Datasets make edge cases cheap to cover.

🏋️ Try it yourself
  1. Build ReadingTime and the two tests above; run php artisan test --filter=ReadingTime.
  2. Add a dataset row for exactly 200 words, and predict the answer before running it.
  3. Create an App\Support\Excerpt class that trims text to N characters and adds "…", then unit test it.
  4. Make the constructor throw InvalidArgumentException for 0 words per minute, and test it with toThrow().
Recap

Key takeaways

  • Unit tests check one class or function in isolation, with no HTTP or database.
  • Create them with php artisan make:test Name --unit; they live in tests/Unit.
  • Pest uses expect($value)->toBe(...); PHPUnit uses $this->assertSame(...).
  • Datasets (->with([...])) run one test against many inputs.
  • Pull logic out of controllers into small classes so it's easy to unit test.
