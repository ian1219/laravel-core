In one sentence

Never let user input become part of your SQL or decide which model columns get filled: use query bindings for the first and $fillable plus validated() for the second.

📮SQL injection is like a form where someone writes “and also give me the keys to the safe” in the name box, and the clerk reads the whole thing out as an order. Mass assignment is like a sign-up form where someone adds an extra line “role: manager” and the clerk copies every line onto the staff card without checking.

Attack #1

How SQL injection works

SQL injection happens when user input is glued directly into a SQL string. The database can't tell where your query ends and the attacker's text begins.

The fix is parameter binding (also called a prepared statement). Your SQL uses a placeholder like ?, and the value is sent separately. The database always treats it as data, never as code.

❌ Interpolated

          SELECT * FROM posts
          WHERE title = '' OR '1'='1'
          -- the input rewrote the query

The condition is now always true.

✅ Bound

          SELECT * FROM posts WHERE title = ?
          -- binding: "' OR '1'='1"

The database searches for a post literally titled ' OR '1'='1 and finds nothing.

Attack #2

How mass assignment works

Mass assignment means filling many model attributes at once from an array, like User::create($request->all()). If you pass along everything the request contains, the attacker chooses the columns.

Step by step

Write queries and saves that can't be hijacked

  1. Use Eloquent and the query builder normally

    Methods like where(), find() and create() bind every value for you. This is safe even with raw user input:

    
          $posts = Post::where('title', 'like', '%' . $request->input('q') . '%')
              ->where('category_id', $request->integer('category'))
              ->get();

    The string concatenation here only builds the value (%term%). Laravel still sends it as a binding.

  2. Going raw? Use ? bindings

    Sometimes you need a SQL expression Eloquent doesn't offer. Methods like whereRaw(), selectRaw(), orderByRaw() and DB::select() accept a bindings array. Put a ? where each value goes.

    
          // ✅ value passed as a binding
          Post::whereRaw('LOWER(title) = ?', [strtolower($title)])->get();

          // ✅ named bindings work too
          DB::select('SELECT * FROM posts WHERE user_id = :id', ['id' => $userId]);
    ⚠️ DB::raw() is never escaped

    DB::raw() tells Laravel "insert this text into the SQL exactly as-is". Never put a PHP variable inside it with "{$var}" or . concatenation.

    
            // ❌ injectable: $sort comes from the URL
            Post::select(DB::raw("*, {$sort} as rank"))->get();

  3. Allow-list column names and sort directions

    Bindings protect values, but you can't bind a column name or asc/desc. When users choose a sort column, check it against a fixed list.

    
          $sort = in_array($request->query('sort'), ['title', 'created_at'], true)
              ? $request->query('sort')
              : 'created_at';

          $dir = $request->query('dir') === 'asc' ? 'asc' : 'desc';

          $posts = Post::orderBy($sort, $dir)->paginate();

  4. Declare $fillable (or $guarded) on every model

    $fillable is an allow-list of attributes that create() and update() may set. Anything else in the array is silently ignored.

    
          <?php

          namespace App\Models;

          class Post extends Model
          {
              protected $fillable = ['title', 'body', 'category_id'];
              // user_id, is_featured, published_at are NOT fillable
          }

    $guarded is the opposite: a block-list. protected $guarded = ['is_admin']; allows everything except is_admin. Prefer $fillable: when you add a new sensitive column later, it's protected by default.

  5. Save only validated() data

    A Form Request's validated() method returns only the fields that have rules. Extra fields the attacker added never reach the model. This is your second lock, on top of $fillable.

    
          public function store(StorePostRequest $request)
          {
              $post = $request->user()->posts()->create($request->validated());

              return redirect()->route('posts.show', $post);
          }

    Notice that user_id comes from the relationship, not from the form. Set ownership and other sensitive values explicitly on the server.

Common mistakes

Avoid this, do that

❌ Avoid

          Post::whereRaw("title = '$title'")->get();

The variable is pasted into the SQL, so a quote in $title rewrites the query.

✅ Do

          Post::whereRaw('title = ?', [$title])->get();
          // or simply:
          Post::where('title', $title)->get();

The value travels as a binding and can never become SQL.

❌ Avoid

          protected $guarded = [];

          $user->update($request->all());

Every column is writable, and every request field is passed in. Two safety nets removed at once.

✅ Do

          protected $fillable = ['name', 'bio'];

          $user->update($request->validated());

Only known, validated fields reach the model, and only allowed columns are written.

💡 Pro tip: make mistakes loud in development

By default, non-fillable fields are dropped silently. Turn that into an exception locally so you notice typos and sneaky fields early.


        use Illuminate\Database\Eloquent\Model;

        public function boot(): void
        {
            Model::preventSilentlyDiscardingAttributes(! app()->isProduction());
        }
🏋️ Try it yourself
  1. Build a post search with Post::where('title', 'like', ...). Search for ' OR '1'='1 and confirm no extra posts appear.
  2. Run Post::whereRaw('LOWER(title) = ?', ['hello'])->toSql() in php artisan tinker and look at the ? placeholder.
  3. Add a sortable posts list that only accepts title or created_at as the sort column.
  4. Add an is_featured column, leave it out of $fillable, and try to set it via Post::create([...]). Check the database.
  5. Enable preventSilentlyDiscardingAttributes and repeat the previous task to see the exception.
Recap

Key takeaways

  • Eloquent and the query builder bind values automatically, so normal where() calls are safe.
  • With whereRaw() and friends, always use ? placeholders plus a bindings array.
  • Never interpolate variables into DB::raw() or any raw SQL string.
  • Bindings can't protect column names or sort directions: allow-list them.
  • Use $fillable as an allow-list of mass-assignable attributes.
  • Pass $request->validated(), not $request->all(), and set ownership on the server.
