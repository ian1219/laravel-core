🙋
“Dependency Injection” sounds like something a doctor does. Should I be scared?
💡
Not at all. It's a fancy name for a simple idea: don't build your own tools, ask for them.
🙋
What's a “dependency” then?
💡
Anything a class needs to do its job. A class that sends order emails depends on a mailer. The mailer is its dependency.
🙋
And “injection”?
💡
Handing that dependency in from the outside, instead of the class making it itself. Think charging port, not glued-in battery. Let me show you.
🧱

The problem: a battery glued inside

When a class builds its own tools, you're stuck with them forever.

🏠 Real life
📱🔋

Imagine a phone with the battery glued in. When the battery dies, or you want a bigger one, you can't swap it. You have to open the whole phone.

=
💻 In code

class OrderService
{
    private EmailNotifier $notifier;

    public function __construct()
    {
        $this->notifier = new EmailNotifier(); // glued in!
    }
}

The word new means “build one right here”. Writing new EmailNotifier() inside the class welds the two together. OrderService can only ever send emails.

Want SMS next month? You edit OrderService. Want to run a test without sending real emails? Tough luck: every test fires a real email at a real customer. 😬

Remember it like this

Seeing new Something() inside a class's constructor is a little alarm bell: “this battery is glued in.”

🔌

The fix: give it a charging port

Ask for the tool in the constructor. Someone else plugs it in.

🏠 Real life
☕

A pod coffee machine doesn't grow its own coffee. It has a slot that accepts any pod of the right shape: espresso, decaf, hot chocolate. Same machine, different drink.

=
💻 In code

class OrderService
{
    public function __construct(
        private Notifier $notifier, // the slot
    ) {}

    public function placeOrder(Order $order): void
    {
        $this->notifier->send("Order #{$order->id} confirmed!");
    }
}

This is constructor injection (passing the tool in through the constructor, the method that runs when an object is created). OrderService no longer cares which notifier it gets. It only says: “give me something that can send().”

That “shape of the pod” is an interface (a contract that lists which methods a class promises to have). Any class that signs the contract fits the slot:


interface Notifier
{
    public function send(string $message): void;
}

class EmailNotifier implements Notifier { /* sends an email */ }
class SmsNotifier implements Notifier { /* sends a text */ }

Now plugging in is your choice, made from the outside:


$service = new OrderService(new SmsNotifier());   // texts today
$service = new OrderService(new EmailNotifier()); // emails tomorrow
Remember it like this

Ask, don't make. A class lists what it needs in its constructor, like a coffee machine with a pod slot. Whoever creates it chooses the pod.

Play with it: with DI on, every notifier plugs straight in. Switch to “Without DI” and try to pick SMS. The class refuses, because the email battery is glued in.

🥤

Laravel plugs things in for you

Meet the service container: a vending machine for objects.

🏠 Real life
🏪

A vending machine: you press “B4” and a drink drops out. You don't care how it was stocked. You just name what you want.

=
💻 In code

class OrderController extends Controller
{
    public function store(StoreOrderRequest $request, OrderService $orders)
    {
        $order = Order::create($request->validated());
        $orders->placeOrder($order);

        return redirect()->route('orders.show', $order);
    }
}

See OrderService $orders in the method's brackets? That's a type-hint (writing the class name before a variable to say “I want one of these”). You never wrote new OrderService(...). Laravel read the type-hint, built an OrderService, noticed it needs a Notifier, built that too, and handed you the finished object.

The thing doing all this is the service container (Laravel's central object factory). It works in controller methods, controller constructors, jobs, listeners, commands and more:


class ReportController extends Controller
{
    public function __construct(
        private ReportBuilder $reports, // Laravel builds and plugs this in
    ) {}
}
ℹ️ Why “automatically” works

For a normal class, the container simply reads the constructor and builds whatever it finds. This is called auto-wiring. You only need to give it instructions when it can't guess, which is our next topic.

Remember it like this

Type-hint it, get it. Write the class name in the brackets, and the vending machine drops the object into your hands.

🏷️

Telling the machine which pod to use

Bind an interface to a real class, once, in one place.

Here's the catch: Notifier is an interface, just a shape. The vending machine can't build a “shape”. You have to tell it: “when someone asks for a Notifier, give them an SmsNotifier.” That's called a binding.


use App\Contracts\Notifier;
use App\Services\SmsNotifier;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->bind(Notifier::class, SmsNotifier::class);
    }
}

That one line rewires your whole app. Every class that asks for a Notifier now gets SMS. Switching back to email? Change one word in one file. Nothing else moves.

💡 Pro tip: bind vs singleton

bind() builds a fresh object every time someone asks. singleton() builds it once and hands out the same one after that, handy for things like an API client you want to set up only once.

Remember it like this

The service provider is the label on the vending machine button: “Notifier → SmsNotifier”. Change the label, change the drink.

🧪

The superpower: easy testing

Swap the real battery for a pretend one.

🏠 Real life
🎭

Film crews use a stunt double for the dangerous scenes. Same costume, no real risk. The movie doesn't know the difference.

=
💻 In code

class FakeNotifier implements Notifier
{
    public array $sent = [];

    public function send(string $message): void
    {
        $this->sent[] = $message; // just remember it
    }
}

In a test you don't want real texts going to real phones. Because OrderService has a slot, you plug in the fake and then check what it “sent”:


public function test_customer_is_notified(): void
{
    $fake = new FakeNotifier();
    $this->app->instance(Notifier::class, $fake); // swap it in

    app(OrderService::class)->placeOrder(Order::factory()->create());

    $this->assertCount(1, $fake->sent);
}

This is a PHPUnit-style test. The same idea works in Pest. And with the glued-in version? This test is impossible without editing the class itself.

Remember it like this

If a class has a slot, a test can plug in a stunt double. No slot, no stunt double, and the real explosions happen every time.

Spot the difference

Glued in vs plugged in

❌ Avoid 

public function __construct()
{
    $this->notifier = new SmsNotifier();
}

The class picks its own tool, so you can't swap it or fake it.

✅ Do 

public function __construct(
    private Notifier $notifier,
) {}

The class asks for any Notifier, and Laravel or your test decides which one.

💡 Pro tip: not everything needs injecting

Simple value objects like new DateTime() or a small data object are fine to create with new. Inject the things that talk to the outside world: mail, SMS, payments, APIs and storage.

🏋️ Try it yourself
  1. In the live demo above, place an order with each notifier, then switch DI off and try to change it. Notice the error message.
  2. Write a Notifier interface and a LogNotifier that calls Log::info($message).
  3. Bind Notifier::class to LogNotifier::class in AppServiceProvider, type-hint OrderService in a controller and check storage/logs/laravel.log.
  4. Change the binding to a different class and confirm you didn't touch OrderService at all.
Key takeaways

What to remember

  • A dependency is a tool a class needs. Injection means handing it in from outside.
  • new inside a class glues the battery in. A constructor parameter gives it a charging port.
  • Type-hint an interface (the pod shape) so any matching class fits the slot.
  • Laravel's service container reads your type-hints and builds everything for you automatically.
  • Use $this->app->bind(Interface::class, Concrete::class) in AppServiceProvider to choose which class fills an interface.
  • DI makes testing easy: swap in a fake and check what it recorded. Ready for more? Read the deep dive on the Service Container.
